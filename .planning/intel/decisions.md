## ADR-0001: One-shot migration step gates API startup
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0001-one-shot-migration-before-api.md
- status: locked (Accepted, 2026-09-16)
- scope: database migrations (Alembic), API startup, Compose `migrate` service, Azure Container Apps Job `careroute-migrate`, deploy ordering, CI migration round-trip check
- decision: Migrations run in a dedicated one-shot process that must exit 0 before the API starts. Locally: Compose `migrate` service with `depends_on: condition: service_completed_successfully`. On Azure: the manual-trigger `careroute-migrate` Container Apps Job. Migrations are baked into the image, so deployed code always carries the schema it expects.
- consequences:
  - A failed migration blocks the release visibly instead of producing a half-working API.
  - Deploys are two steps (run migrate job, then roll the app); forgetting the first is the main operational risk. A CI deploy step should enforce the order. (Open work, see PRD R2.)
  - Autogenerated Alembic migrations must be reviewed: autogenerate omits `DROP TYPE` for native enums, breaking downgrade/upgrade round-trips. CI checks the round-trip.

## ADR-0002: Separate liveness and readiness probes
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0002-separate-liveness-and-readiness.md
- status: locked (Accepted, 2026-09-23)
- scope: `/health` liveness, `/ready` readiness, container HEALTHCHECK, Container Apps liveness/readiness probes, ingress routing, `pool_pre_ping`
- decision: `/health` (liveness) never touches the database and always returns 200 while the process is alive. `/ready` (readiness) runs `SELECT 1` and returns 503 when the database is unreachable, logging the underlying error rather than returning it (endpoint is public). Container HEALTHCHECK and Container Apps liveness use `/health`; Container Apps readiness uses `/ready`.
- consequences:
  - "Container healthy" does not mean "service working"; the runbook tells on-call to check `/ready`.
  - With the DB down, `/ready` 503s and ingress stops routing; the API recovers on its own when the DB returns (`pool_pre_ping`), verified by drill.

## ADR-0003: JWT bearer auth with a per-request user re-check
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0003-jwt-with-per-request-user-check.md
- status: locked (Accepted, 2026-09-23)
- scope: authentication, OAuth2 password flow, `/auth/token`, HS256 JWT, argon2id, roles (viewer, clinician, coordinator), `JWT_SECRET`
- decision: OAuth2 password flow issues short-lived (60 min) HS256 JWTs. Passwords are argon2id-hashed. On every request the user is re-loaded from the database and `is_active`/`role` come from the database, not the token. Login returns an identical 401 for unknown email, wrong password and inactive account, verifying against a dummy hash for unknown emails so timing matches. The app refuses to start outside local/dev/test with the built-in dev `JWT_SECRET`.
- consequences:
  - Deactivation and demotion take effect on the next request (verified live). Cost: one primary-key lookup per request.
  - Rotating `JWT_SECRET` invalidates every token at once; this is the emergency lever in the incident process.
  - Not yet done: rate limiting and failed-login logging on `/auth/token` (see PRD R4), refresh tokens and RS256 (PRD lists these as out of scope).

## ADR-0004: Audit trail actor comes from the authenticated identity
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0004-audit-actor-from-token.md
- status: locked (Accepted, 2026-09-23)
- scope: `referral_events.actor`, audit trail, referral status changes, Pydantic request models
- decision: Request bodies carry no `actor`; `referral_events.actor` is set to the authenticated user's email. An `actor` sent anyway is ignored (Pydantic drops unknown fields). A test submits a spoofed actor and asserts the real identity is recorded.
- consequences:
  - The audit trail is trustworthy for status changes.
  - Known gaps (listed in INCIDENT-RESPONSE.md, out of ingest scope): reads are not logged and provider assignment is not logged. (Open work, see PRD R5.)

## ADR-0005: Docker Hardened Images as the base image
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0005-docker-hardened-images.md
- status: locked (Accepted, 2026-09-23)
- scope: Dockerfile base images, multi-stage virtualenv, non-root runtime, multi-arch, CI Trivy gate, Docker Scout VEX, `DOCKERHUB_*` secrets
- decision: Build on `dhi.io/python:3.12-debian13-dev` and run on `dhi.io/python:3.12-debian13`: no shell, no package manager, non-root uid 65532, app files root-owned and read-only to the process. Both share `/usr/bin/python3.12`, so the build-stage virtualenv runs unchanged. Images are multi-arch (amd64 + arm64).
- consequences:
  - Image size 325 MB to 234 MB. CI's Trivy gate fails on any fixable HIGH/CRITICAL.
  - Plain Scout scan lists six base-image HIGHs; Docker's VEX marks all six `not_affected` (0/0 with `--vex-location`). Attaching VEX to the image was tested and Scout did not apply it, so docs state the accurate status rather than claiming a clean scan.
  - Builds and CI need a Docker account to pull from dhi.io (`DOCKERHUB_*` secrets).
  - No shell for debugging; use `docker debug`.

## ADR-0006: Terraform state in a separate, Entra-only storage account
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0006-terraform-state-backend.md
- status: locked (Accepted, 2026-09-24)
- scope: Terraform state backend, Azure Storage, resource groups `careroute-tfstate-rg` / `careroute-rg`, `infra/backend-setup/setup-backend.sh`, `backend.hcl`, Entra ID auth, RBAC
- decision: State lives in Azure Storage bootstrapped by `infra/backend-setup/setup-backend.sh` (Azure CLI), in its own resource group `careroute-tfstate-rg`, separate from the app's `careroute-rg` (whose documented cleanup deletes the whole group). The account allows Entra ID auth only (shared keys disabled; verified refused), HTTPS/TLS 1.2, no public access, blob versioning with 30-day soft delete, and a CanNotDelete lock. The account name is subscription-derived and passed at init via `backend.hcl` (partial backend config).
- consequences:
  - No storage keys exist to leak; access is governed by RBAC on the account.
  - The state blob holds secrets: anyone with Storage Blob Data Reader on it can read them.

## ADR-0007: Private-access Postgres, deployed to Central US
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0007-private-postgres-in-centralus.md
- status: locked (Accepted, 2026-09-24)
- scope: Azure Database for PostgreSQL Flexible Server, VNet/delegated subnets, private DNS, Container Apps environment, TLS, region
- decision: Postgres 16 Flexible Server (B1ms) is VNet-injected into a delegated subnet with a private DNS zone and `public_network_access_enabled = false`. The Container Apps environment runs in another delegated subnet of the same VNet. TLS required (`sslmode=require`). The app is deployed to centralus (subscription is restricted from Postgres Flexible Server in eastus, eastus2, westus2); Terraform state storage stays in eastus.
- consequences:
  - No public database endpoint and no firewall rule to get wrong.
  - No direct `psql` from a laptop; use a job/container inside the VNet or a jump host.
  - The app currently connects as the server admin; a dedicated least-privilege role is open work (see PRD R6).

## ADR-0008: Secrets generated by Terraform into Key Vault, read via managed identity
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0008-secrets-generated-into-key-vault.md
- status: locked (Accepted, 2026-09-24)
- scope: Terraform `random_password`, RBAC-mode Key Vault, user-assigned managed identity, Container App and jobs, DB password, `JWT_SECRET`, demo passwords, tfplan handling
- decision: Terraform's `random_password` generates every secret and writes it to an RBAC-mode Key Vault. The deployer gets Key Vault Secrets Officer; a user-assigned managed identity gets Key Vault Secrets User and is the only thing the Container App and jobs use to read secrets (versionless references, so rotation needs no Terraform change). A 90-second `time_sleep` covers RBAC propagation.
- consequences:
  - No human ever sees or types a production secret.
  - Secrets are also in Terraform state (see ADR-0006).
  - Plan files embed secrets; `*.tfplan` is git-ignored.

## ADR-0009: Public demo exposes only a read-only login
- source: /Users/kyleharrington/Desktop/AI/Docker/CareRoute/docs/adr/0009-read-only-public-demo.md
- status: locked (Accepted, 2026-09-24)
- scope: seed script, `--demo-deployment`, `--reset`, demo accounts, `DEMO_CLINICIAN_PASSWORD` / `DEMO_COORDINATOR_PASSWORD`, public demo
- decision: The seed runs outside local/dev/test only with `--demo-deployment`. Then only `viewer@careroute.demo` gets the published password; clinician and coordinator get private passwords from `DEMO_CLINICIAN_PASSWORD` / `DEMO_COORDINATOR_PASSWORD` (Key Vault, min 16 chars, never the published value), and `--reset` is refused. The policy is a pure function with its own tests.
- consequences:
  - Anyone can browse the demo; only the owner can demonstrate writes.
  - `/auth/token` is internet-facing without rate limiting, so private passwords are long and random; rate limiting is open work (see PRD R4).
