<task type="auto">
  <name>Task 2: scripts/db_roles.py, the idempotent bootstrap</name>
  <files>scripts/db_roles.py</files>
  <read_first>02-RESEARCH.md (the verified order), scripts/seed.py (for logging/argparse style)</read_first>
  <action>
Python 3.12, psycopg 3 only (no app imports, so it runs without JWT_SECRET/APP_ENV concerns). Match seed.py's style: module docstring with usage, `logging`, `main() -> int`.
Env inputs: `ADMIN_DATABASE_URL` (a SQLAlchemy-style URL; strip the `+psycopg` driver suffix before `psycopg.connect`), `MIGRATE_DB_PASSWORD`, `APP_DB_PASSWORD`, optional `MIGRATE_DB_ROLE` (default careroute_migrate), `APP_DB_ROLE` (default careroute_app). Fail with a clear message if any is missing. Never log a password or URL.
Steps, in one transaction (autocommit off), in exactly this order (see RESEARCH):
1. For each role: create it with `CREATE ROLE ... LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE` if it's not in `pg_roles`; then always `ALTER ROLE ... WITH LOGIN PASSWORD <literal>`. Use `psycopg.sql.Identifier` / `sql.Literal`. Password sync on every run is the rotation mechanism.
2. `GRANT <migrate> TO current_user WITH INHERIT FALSE, SET TRUE`, skipped when current_user is a superuser (Compose). Idempotent in PG16.
3. `GRANT CONNECT ON DATABASE <current_database()> TO` both; `GRANT CREATE, USAGE ON SCHEMA public TO <migrate>`; `GRANT USAGE ON SCHEMA public TO <app>`.
4. Transfer ownership to migrate for every object in `public` not already owned by it: tables (relkind r, p), views (v), materialized views (m), standalone sequences (S, only when not owned by a column, i.e. no `pg_depend` deptype 'a' entry), and enum/domain types (typtype e, d; skip array types, typelem <> 0 or name starting `_`).
5. `SET ROLE <migrate>`; `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO <app>`; `GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO <app>`; `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO <app>`; same for sequences; `REVOKE ALL ON alembic_version FROM <app>` if the table exists; `RESET ROLE`.
6. Commit. Log a summary: roles present, number of objects whose ownership moved, and "passwords synced" (no values).
Exit 0 on success, 1 on error (after rollback).
Known gap to document in the SUMMARY: step 5's `REVOKE ... alembic_version` runs before the first migration on a fresh DB, so default privileges will grant the app DML on alembic_version when migrate first creates it. Task 3 therefore also runs db-roles **after** migrate in the test stack, or re-issues the revoke. Choose the smaller correct option and justify it.
  </action>
