# ADR-0001: One-shot migration step gates API startup

- **Status:** Accepted
- **Date:** 2026-09-16

## Context

The API must never serve traffic against a schema that hasn't been migrated, and several API replicas must not race to run migrations.

## Decision

Migrations run in a dedicated one-shot process that must exit 0 before the API starts. Locally that's the Compose `migrate` service (`depends_on: condition: service_completed_successfully`); on Azure it's the manual-trigger `careroute-migrate` Container Apps Job. Migrations are baked into the image, so deployed code always carries the schema it expects.

## Consequences

- A failed migration blocks the release visibly instead of producing a half-working API.
- Deploys are two steps (run migrate job, then roll the app); forgetting the first is the main operational risk. A CI deploy step should enforce the order.
- Autogenerated Alembic migrations must be reviewed: autogenerate omits `DROP TYPE` for native enums, which breaks downgrade→upgrade round-trips. CI checks the round-trip.
